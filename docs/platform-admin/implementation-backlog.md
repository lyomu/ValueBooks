Needs an owner decision because it changes who may do what. | ⛔ needs owner |
| O5 | **Direct plan edits removed from the console UI (4.1).** The old Plans page let a superadmin edit a live plan's entitlements inline and set `isDefault`. The audited API endpoints are unchanged, so an emergency correction remains possible. **Owner to decide:** build the controlled change workflow (propose → preview → approve → publish), or accept catalog changes as migrations only. | ⛔ needs owner |
| O6 | **D12, renewal payments not applied (billing, P1).** **Owner decision 2026-10-22: fix it, and report past drops without backfilling.** Done: paid `invoice.update` is handled by subscription code; a renewal `charge.success` is matched by customer + plan code and refused when more than one subscription fits; amount and currency are checked as before, and one transaction is recorded per charge reference. The read-only [dropped-renewals report](runbooks/dropped-renewals-report.md) lists past drops; correcting any of them needs the owner's approval per row. **The production run of the report is the owner's** (no production access here). | ✅ (report run pending in production) |
| O7 | **Country pack review states (found in 5.2, not built).** Spec §12.2 describes `DRAFT → IN_REVIEW → APPROVED → PUBLISHED → DEPRECATED`. The domain has only `DRAFT → PUBLISHED → DEPRECATED`, and a single superadmin can publish a version (now with a reason, the identifier typed back and an impact statement). Adding review and approval states needs a migration and a second-approver rule like refunds and overrides have. **Owner to decide** whether publication needs a second approver. | ⛔ needs owner |
| O8 | **Retrying a recurring posting can create nothing (found in 5.3, not changed; accounting code).** Recurring invoices, bills, expenses and journals claim a ledger idempotency key per occurrence *before* creating the document (`recurring-bills.service.ts` `claimOccurrence`). A retry therefore never duplicates a document. But if the failed run had already claimed the occurrence and then failed, the retry finds the claim and creates nothing. The document has to be created by hand. The console's retry dialog and details drawer say so. **Owner to decide** whether a failed run should release its claim (in the same transaction as the failure) so a retry can complete it. | ⛔ needs owner |
